# Writing style

These rules apply to everything written in this repo: user-facing strings in
`messages/`, code comments, commit messages, docs, and Prisma schema notes.

## No em dashes, no middle dots

Do not use `—` (em dash) or `·` (middle dot).

When an em dash is holding a sentence together, **rewrite the sentence** so the
dash is not needed. Do not swap it for another dash, and do not reach for a
semicolon either. Most people writing by hand use neither. In order of
preference:

1. Split it into two sentences.
2. Use a comma.
3. Use parentheses for a genuine aside.
4. Use a colon when the second half explains or lists.

```
Bad   The check asks only whether a value is there — so the value can be wrong.
Bad   The check asks only whether a value is there – so the value can be wrong.
Bad   The check asks only whether a value is there; so the value can be wrong.
Good  The check asks only whether a value is there. The value itself can be wrong.
Good  The check asks only whether a value is there, so the value can be wrong.
```

## Separators in UI labels

Use `–` (en dash, U+2013) to join a code and its name, or to separate fields on
one line: `3001 – Försäljning`, `{km} km – {rate} kr/km`, `2026 – Ursprunglig`.
This is the one place a dash character is wanted.

## Exceptions

Three existing uses of `·` are deliberate and must stay:

- `src/lib/fortnox/sie.ts` – the CP437 codepage table. Editing it corrupts SIE export.
- `src/app/(app)/budget/[budgetId]/budget-helpers.ts` – `·` is parsed as a multiplication operator in budget formulas.
- `····{last4}` card masks in `messages/`, `admin/cards/`, `columns/bank-columns.tsx` – a four-dot mask, not a separator.

The `nextjs-agent-rules` block above is regenerated by `next dev` and contains
em dashes. Leave it alone. Cleaning it only re-creates an uncommitted change.
